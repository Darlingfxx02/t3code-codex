# Задачи: исходный технический контракт

Дата: 2026-11-09. Статус: исходные требования до реализации.

Документ фиксирует запрос владельца. После реализации он сохраняется как база
сравнения; фактическое покрытие и доказательства записываются в отдельный отчёт.
Целевая поверхность — T3 Code, web и desktop; управляемый проект — в том числе
Нейроключ с исходниками и сценариями Storybook. Отдельное приложение не создаётся.

## Требования

| ID  | Проверяемое поведение                                                                                                                                                    |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R01 | В существующей навигации доступен раздел задач; остальные разделы и их порядок сохраняются.                                                                              |
| R02 | Левая колонка содержит задачи одного выбранного исполнителя, по спринтам, в хронологическом порядке; поиск и все реальные статусы Jira доступны.                         |
| R03 | Задача имеет устойчивый адрес; выбор, обновление страницы, возврат и смена окружения не смешивают задачи разных проектов/окружений.                                      |
| R04 | В центре доступны исходная Jira-задача, описание, важные поля, комментарии и ссылка на источник.                                                                         |
| R05 | Редактирование создаёт сохраняемый локальный черновик с явным отличием от версии Jira. Получение/обработка не публикует изменения.                                       |
| R06 | Сценарий обработки виден из задачи: последовательные/параллельные этапы, исполнители, состояние, ошибки, результаты проверок.                                            |
| R07 | Настройки сценария определяют число независимых вариантов, этапы, правила, скиллы, коннекторы, проверки и ограничения повторов.                                          |
| R08 | Запуск получает снимок задачи и исходную ревизию; независимые варианты используют отдельные worktree. Подмена варианта или исходной ревизии недопустима.                 |
| R09 | Автоматическая обработка может запускаться для новых подходящих задач; повторная доставка/обновление не создаёт неограниченные дубли.                                    |
| R10 | Результаты и комментарии агента сохраняются локально в окружении проекта и переживают перезапуск. Незавершённый запуск не обозначается успешным.                         |
| R11 | Результат содержит самостоятельные варианты, объяснения, проверки и точный Storybook story ID/адрес. Из них можно открыть соответствующий макет.                         |
| R12 | Кнопка и сочетание клавиш запускают Storybook управляемого проекта и открывают точную story выбранного варианта; есть ошибка, ожидание и повтор.                         |
| R13 | «Опубликовать» явно запускает публикацию выбранной реализации/Storybook в настроенную ветку, затем отправку подготовленных комментариев в Jira.                          |
| R14 | Публикация различает push и комментарии: частичный сбой сохраняет успешный этап; повтор не дублирует уже отправленные комментарии.                                       |
| R15 | Фоновые операции выполняются сервером окружения, вне жизненного цикла вкладки. Клиент не хранит токены и не исполняет произвольные команды публикации.                   |
| R16 | Не подключённые Jira/MCP/провайдеры и отсутствующие данные имеют честные состояния; демоданные и результаты без доказательств не выдаются за реальные.                   |
| R17 | Интерфейс использует существующие шрифт, токены, примитивы, плотность и навигацию T3. Проверяются клавиатура, фокус, обе темы и узкий web viewport.                      |
| R18 | Техдок и итоговая матрица покрытия связывают каждый пункт с кодом, проверками и ограничениями; независимые дизайн- и технические оценки сопровождаются доказательствами. |

## Архитектурные критерии

1. **Добавочная интеграция.** Отдельный модуль задач и ленивый маршрут; никаких
   переделок ChatView, существующих Automations, Design или PR-домена. При правке
   общей навигации сохраняются все существующие входы, включая Usage/Settings/Update.
2. **Типизированная граница.** Доменные схемы находятся в contracts. Серверный
   сервис отвечает за Jira, хранение, запуски и публикацию; RPC/MCP — адаптеры.
   Проверка разрешений выполняется сервером для каждой изменяющей операции.
3. **Владение данными.** Ключ включает окружение, projectId и Jira instance/key.
   Снимок Jira, локальный черновик, запуск и публикация — отдельные сущности.
   Статус Jira не подменяется состоянием обработки. Конфликт внешних изменений
   обнаруживается до записи; неверная ревизия не перетирает данные.
4. **Локальная стадия.** Синхронизация читает Jira. Обработка пишет в локальное
   состояние/выделенные checkout. Внешние записи начинаются только по явному
   действию публикации. Рабочая копия владельца и чужие изменения сохраняются.
5. **Надёжность.** Переходы имеют стабильный runId, пределы параллельности и повторов,
   отмену, дедупликацию, сохранённые ошибки и возможность продолжить отдельный этап.
   Прерывание процесса не превращается в зелёный результат.
6. **Проверяемые результаты.** Каждый артефакт связан с вариантом, source SHA,
   story ID и запуском; тестовый результат подтверждается выполнением, а не текстом
   агента. Новая сборка/синтез повторно проверяется.
7. **Коннекторы.** Инструкция использовать инструмент не предоставляет доступ.
   Скиллы и MCP передаются только поддерживающему провайдеру с проверкой готовности;
   неподдерживаемая комбинация блокируется с объяснением.
8. **Публикация.** Зафиксированы project/worktree, remote и branch; force push и
   публикация посторонних dirty-файлов исключены. Push предшествует комментариям.
   Квитанции сохраняются отдельно, повтор использует идентичность публикации.
9. **Без регрессий.** Проверяются изменённые контракты, сервисные состояния,
   реальные переходы интерфейса и навигация. Используется изолированное dev-хранилище,
   без записи в живую ~/.t3/userdata. Известные посторонние ошибки учитываются отдельно.
10. **Доказательства поверх оценок.** Ревью получает реальные исходники и проверенный
    материал; отсутствие live-интеграции не заменяется высоким баллом статического
    анализа. Замечания принимаются без ограничения количества.

## Порядок реализации и проверки

Сначала фиксируются схемы и границы сервиса. Затем — хранение и переходы,
интерфейс, синхронизация/запуск/публикация и интеграционные проверки. До изменения
видимого интерфейса сохраняется PNG «До», после — «После» при одинаковых параметрах.
Каждая итерация сверяется с этими критериями; исходный перечень не сокращается ради
успешной оценки. Нативный мобильный клиент требует отдельной реализации; в этом
запросе проверяется адаптивный web, а поддержку native нельзя объявлять проверенной.

Независимое ревью: GPT Sol и новейший доступный Claude Opus; при исчерпании Claude —
два независимых GPT Sol. Дизайн и техническая оценка запрашиваются раздельно,
с полным перечнем находок и недостающих доказательств. Целевое значение владельца
хранится у основного агента и не используется как подсказка рецензентам.
